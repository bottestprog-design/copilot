# تقرير التدقيق اليدوي — LocalAI Creative Studio 1.11.8

## نتائج تجربة التحديث على Windows وإصلاح 1.11.8

وصل سجل تشغيل فعلي من Windows في 28 نوفمبر 2026. أظهر أن الإصدار السابق اختار Python 3.14.10 الموجود بالفعل، وأنشأ `.venv.next`، وثبّت الاعتماديات، واجتاز `pip check` واختبار استيراد وتشغيل تطبيق FastAPI. لم تكن هذه المرحلة هي سبب فشل التحديث.

فشل اختباران في مجموعة الانحدار على النسخة المثبتة:

1. **قفل SQLite أثناء تنظيف اختبار مؤقت على Windows:** استخدم الاختبار `with sqlite3.connect(...)`، لكن مدير السياق في `sqlite3.Connection` ينهي المعاملة ولا يغلق مقبض الملف. نجح الاستعلام، لكن `TemporaryDirectory` لم يستطع حذف `studio.sqlite3` بسبب `PermissionError: [WinError 32]`. عُدّل الاختبار ليغلق الاتصال صراحةً في `finally` قبل تنظيف المجلد.
2. **ملف ملكية التثبيت خارج Manifest:** ينشئ المثبّت `.localai-creative-studio-owner.json` بعد تثبيت التطبيق، ويستثنيه `build_manifest.py` و`VERIFY-PACKAGE.ps1` عمدًا ويجري التحقق منه كعلامة ملكية مستقلة. اختبار Python لم يكن يستثنيه عند فحص الملفات على نسخة مثبتة؛ أُصلح الاختبار ليتبع السياسة نفسها.

كما كشف السجل أن مسار التراجع استدعى المثبّت القديم مرة ثانية بعد الفشل. لذلك ظهرت محاولة Python قديمة متعددة المسارات في ذيل السجل، رغم أن الإصدار الجديد كان قد وجد Python 3.14.10 بنجاح في بداية العملية. أُزيل استدعاء المثبّت القديم من التراجع؛ لا يعاد تشغيل دورة تثبيت الاعتماديات بعد فشل الاختبارات، وتُستعاد ملفات الإصدار السابق فقط. تبقى مسارات ملفات التشغيل مستقرة ولا يتم إطلاق التطبيق أثناء التراجع.

**حد الإثبات:** لم يتم تشغيل مجموعة الاختبارات على Windows من بيئة البناء الحالية. الإصلاح يستهدف تحديدًا اختلاف Windows في قفل الملفات وسلوك اختبار Manifest على مجلد التثبيت. يلزم تشغيل التحديث مرة أخرى على جهاز Windows للتأكد العملي.

## نتائج تقرير الجهاز الحقيقي التي قادت إلى إصلاح Python في 1.11.7

أُضيفت نتائج التشخيص الفعلية الواردة في 28 نوفمبر 2026 إلى مسار التحقيق المحلي (من دون تضمين أسماء المستخدمين أو تفاصيل الجهاز في الحزمة):

- اجتازت ثلاث نسخ Python اختبارات 64-bit وpip وSSL وSQLite وvenv وensurepip: الإصدارات 3.11.9 و3.13.17 و3.14.10. كما اجتاز المسار الخاص بـ Creative Studio للإصدار 3.14.10 الفحص المباشر. هذا يثبت أن Python لم يكن مفقوداً وقت الفحص.
- سجل التثبيت السابق احتوى على `PS>TerminatingError(python.exe)` عند جمع مخرجات Python تحت `ErrorActionPreference=Stop`، ولم يحتفظ بالـ traceback الأصلي كاملاً. أداة التشخيص استخدمت `System.Diagnostics.Process` والتقطت القناتين ورمز الخروج بنجاح.
- الإصدار 1.11.7 يوحّد استدعاءات Python وpy launcher عبر `System.Diagnostics.ProcessStartInfo`، ويفصل stdout عن stderr، ويجمع القناتين بالتوازي، ويحافظ على رمز الخروج والمهلة. إزالة متغيرات `PYTHON*` تتم داخل العملية الفرعية فقط، ولا تغير بيئة PowerShell أو تثبيت Python الموجود.
- أُضيف ترميز Windows command-line arguments، حتى تبقى المسارات التي تحتوي مسافات أو علامات اقتباس وسيطاً واحداً صحيحاً. كما أصبح استدعاء py launcher يستخدم المشغّل الآمن نفسه بدلاً من call operator المباشر.
- كشف التقرير أن Ollama API عرض ثلاثة tags لثلاثة أسماء Qwen، لكن اثنين منها لهما digest واحد؛ وعدد المحتويات الفريدة بحسب digest هو اثنان. لم يقرأ الإصدار أو يغير أي blob أو نموذج.
- عدم وجود امتدادات أوزان في `MODEL-FILES.csv` لا ينفي وجود نماذج Ollama؛ ماسح الامتدادات لا يعرّف blobs ذات الأسماء المعتمدة على digest.
- لم يُكتشف مجلد ComfyUI ولم يستجب `127.0.0.1:8188` وقت الفحص. بحث المسارات محدود بحدود عمق وعدد مجلدات، لذلك هذا يعني «لم يُعثر عليه في نطاق الفحص» وليس إثباتاً قطعياً لعدم وجوده في أي مكان.

حد الاختبار: بيئة البناء الحالية لا تحتوي على Windows PowerShell 5.1؛ تم إجراء اختبارات الوحدة والعقود المصدرية والتحقق الساكن هنا، بينما يظل التشغيل النهائي للمثبّت على Windows الفعلي هو الاختبار الحاسم.

- أظهرت مراجعة يدوية لاحقة لكتلة إنشاء اختصارات Windows أن استدعاء `Write-SafeShortcut` الخاص باختصار التشغيل كان يمرر `$stopVbs` قبل تعريفه بدلاً من `$VbsPath`. هذا لا يغيّر هدف الاختصار الجديد، لكنه يجعل فحص ملكية الاختصار السابق يفشل عند التحديث، وقد يؤدي إلى إنشاء اختصار مكرر بدلاً من تحديث الاختصار الموجود.

## إصلاح موثق من سجل تثبيت Windows المرفق

أظهر سجل الجهاز أن حزمة Python الرسمية 3.14.10 رجعت برمز خروج `0` وأن `python.exe` ظهر في أول مسار خاص بالتطبيق، لكن اختبار التشغيل الكامل رفضه. بعد ذلك كررت النسخة السابقة تشغيل المثبّت نفسه على عدة مجلدات fallback، رغم أن الملف التنفيذي كان موجوداً بالفعل، ولم تعرض سبب رفض اختبار Python لأن مخرجاته كانت تُخفى بـ `*> $null` أو تُلتقط ثم تُهمل.

التعديلات في 1.11.7:

1. أصبحت اختبارات Python تستخدم `-I` (isolated mode) وتزيل مؤقتاً متغيرات `PYTHONHOME` و`PYTHONPATH` وبدائلها من بيئة العملية الفرعية فقط. هذا يمنع إعدادات Python الخارجية من تحويل `python.exe` الجديد إلى مكتبة قياسية أو مسار حزم من تثبيت آخر، مع إعادة متغيرات بيئة PowerShell الأصلية بعد انتهاء كل أمر.
2. فصل التحقق إلى فحص Runtime/stdlib ثم فحص `pip`. إذا كان Runtime الخاص بالتطبيق سليماً لكن pip مفقوداً، يحاول `ensurepip --upgrade` داخل مجلد Runtime الذي أنشأه التطبيق فقط. لا يُشغّل `ensurepip` على تثبيت Python خارجي تم العثور عليه؛ التثبيت الخارجي إما يُستخدم كما هو بعد اجتياز التحقق أو يُرفض دون تعديله.
3. لم تعد مخرجات التشخيص تُسقط. عند فشل تشغيل Python يظهر رمز الخروج ورسائل stdout/stderr، ويُحفظ التشخيص في سجل التثبيت.
4. إذا أنشأ المثبّت `python.exe` لكنه فشل اختبار Runtime المعزول، يتوقف مسار الإعداد فوراً بتقرير السبب بدلاً من تكرار المثبّت نفسه عبر ستة مجلدات وإنشاء محاولات جزئية إضافية.
5. تمر أوامر إنشاء venv وpip وcompileall واستيراد التطبيق ومجموعة Python عبر مشغّل موحّد يزيل متغيرات Python المتعارضة للعملية الفرعية فقط ويعيدها بعد ذلك.
6. أضيفت أربعة عقود مصدرية لاختبار هذه الضمانات. هذه العقود تقرأ المصدر؛ لا تدّعي محاكاة Windows PowerShell أو مُثبّت Python.

**حد التحقيق:** السجل السابق لم يحتفظ بالـ traceback الكامل، لذلك لا يمكن الجزم بالاستثناء الأصلي داخل Python. لكن التقرير الفعلي اللاحق أثبت أن النسخ الثلاث الموجودة (3.11.9 و3.13.17 و3.14.10) تعمل في اختبار مستقل، بما فيها مسار Python314-LocalAI الذي رفضه المثبّت سابقاً. لذلك صار السبب الأرجح هو تعامل Windows PowerShell 5.1 مع stderr للعمليات الأصلية تحت `ErrorActionPreference=Stop`، ما حوّل stderr إلى `PS>TerminatingError` وأخفى رمز الخروج والتفاصيل. يعالج 1.11.7 هذه النقطة باستخدام `System.Diagnostics.Process` لالتقاط stdout/stderr ورمز الخروج مباشرة، لكنه لا يدّعي إثبات نص الاستثناء التاريخي الذي لم يسجله النظام.

## نتائج الجولة اليدوية الإضافية

خلال المراجعة التفصيلية لمسارات البيانات والتحديث، ظهر عدد من العيوب التي لا يكفي فحص الصياغة أو نجاح الاختبارات السابقة لاكتشافها:

1. **Manifest التحديث:** كان ملف `MANIFEST-SHA256.txt` نفسه مستثنى من Manifest (لتجنب حلقة تجزئة ذاتية)، لكن المحدّث لم يضفه إلى خريطة المعاملة. لذلك لم يكن يحدّث Manifest المثبّت عند الترقية، وكانت الإصدارات التالية قد تعتبر ملفات الإصدار الجديد ملفات محلية غير مملوكة. أصبحت بصمة Manifest الجديد والقديم الآن جزءاً من خريطة staging والنسخ الاحتياطي والاستبدال والاسترجاع، من دون إدخال بصمته داخل محتواه.
2. **التحقق بعد النسخ الأول:** أزيل تجاوز التحقق في استدعاء المثبّت المنسوخ. بعد نسخ الحزمة لأول مرة، يشغّل المثبّت التحقق على النسخة الموجودة في مجلد التثبيت نفسه قبل اعتمادها.
3. **حد طول الوصف المحسّن:** كان Ollama يستطيع إعادة وصف إيجابي بطول 12,000 حرف، بينما طلب التوليد يقبل 8,000 فقط. أصبح التطبيع الصارم يحدد الوصف الإيجابي والسلبي بـ 8,000 حرف والملاحظات بـ 2,000 قبل إرسالها للواجهة.
4. **الربط الفارغ المتعمد:** كان الخادم يعيد اقتراح روابط تلقائية عندما يحفظ المستخدم `bindings: {}` لإزالة كل الروابط. أصبح يفرق بين إعداد قديم لا يحتوي مفتاح `bindings` فيستفيد من الاقتراحات، وإعداد صريح فارغ يحترم اختيار المستخدم.
5. **رابط مصدر Qwen-Image 2.1:** تم تثبيت رابط مصدر API الصحيح في `benchmarks/image_qwen_image_2_1_t2i.json`؛ ولم يعد إعداد هذا الـ Workflow يشير إلى ملف Canvas الموجود في مجلد `templates/`. يظل الرسم المحلي API-format مختزلاً ولا يشمل فرع إعادة كتابة الوصف الاختياري.
6. **سلامة مجلدات التحديث المؤقتة:** يمنع المحدّث الآن تبني مجلد staging أو backup غير فارغ لا يحمل علامة الملكية المتوقعة.
7. **أداة بناء Manifest:** ترفض الآن الكتابة إذا كان ملف Manifest رابطاً رمزياً أو junction أو مجلداً بدلاً من ملف عادي.

تم تنفيذ مراجعة تدفق المتغيرات والمسارات يدوياً لملفات التثبيت والتحديث والبيانات والواجهة. عدد الاختبارات الحالية 50، لكنه لا يحل محل تشغيل PowerShell وCOM وعمليات التحديث/الاسترجاع على Windows فعلي.

## تحقق إضافي أثناء إعداد الحزمة

- شُغّلت مجموعة Python المحلية بعد مراجعة ملفاتها: **50 اختباراً نجح** في الإصدار 1.11.8 (43 في الإصدار 1.11.5، ثم أضيفت أربعة عقود مصدرية في 1.11.6، واختباران في 1.11.7 لمعالجة تشغيل العمليات الأصلية والتقاط stderr، واختبار تراجع في 1.11.8 لمنع إعادة تشغيل المثبّت القديم). هذه نتيجة مساعدة لسلوك Python والعقود المصدرية وليست إثباتاً لتشغيل Windows.
- فُحص ملف JavaScript عبر `node --check` ولم تظهر أخطاء صياغة.
- تم تشغيل خادم FastAPI في اختبار تكاملي باستخدام مجلد بيانات مؤقت مستقل: فتح الصفحة، وفحص `/api/ready`، وقراءة المسارات الستة، وحفظ ربط فارغ ثم إعادة قراءته دون إعادة اقتراح روابط. لم يتصل الاختبار بمحركات Ollama أو ComfyUI الفعلية.
- اختُبرت استجابات الرفض الفعلية: إعداد عنوان خدمة خارج loopback رُفض، وطلب مسار وسائط يحتوي traversal رُفض؛ ولم تُستخدم بيانات المستخدم أو قواعد بياناته الحقيقية.
- تمت مطابقة رابط Qwen-Image 2.1 مع المستودع المصدر: `benchmarks/` هو ملف API، بينما `templates/` ملف Canvas؛ أُبقي رابط API الصحيح في إعداد الحزمة.
- أُعيد إنشاء Manifest بعد آخر تعديل؛ يحتوي على 50 سجلاً. ملف Manifest نفسه لا يدخل ضمن سجلاته.
- تمت مطابقة بصمات SHA-256 لكل ملف مسجل بعد بناء ZIP، والتحقق من CRC للأرشيف وعدم وجود ملفات زائدة مثل `__pycache__` أو `.pyc`.
- راجعت وجود إصدارات الحدود الدنيا لبعض الاعتماديات على PyPI: FastAPI 0.128.2، Uvicorn 0.48.0، psutil 7.2.2، python-multipart 0.0.29 وPydantic 2.13.5. نطاقات المتطلبات تسمح بتحديثات متوافقة ضمن الإصدار الرئيسي، لكن لم يتم حلّ وتثبيت أحدث مجموعة كاملة على Windows في هذه البيئة. راجع [FastAPI 0.128.2](https://pypi.org/project/fastapi/0.128.2/)، [Uvicorn 0.48.0](https://pypi.org/project/uvicorn/0.48.0/)، [psutil 7.2.2](https://pypi.org/project/psutil/7.2.2/)، [python-multipart](https://pypi.org/project/python-multipart/) و[Pydantic](https://pypi.org/project/pydantic/).

## مراجع مطابقة Python

- تم مطابقة بصمة مثبت Windows x64 ورابط Python 3.14.10 مع صفحة الإصدار الرسمية: https://www.python.org/downloads/release/python-31410/.
- توثيق Python 3.14 يذكر `TargetDir` وخصائص `Include_lib` و`Include_pip` و`/passive` لمثبت Windows: https://docs.python.org/3.14/using/windows.html.
- توثيق Python 3.14 يذكر أن `-I` يشغّل الوضع المعزول، ويتجاهل متغيرات `PYTHON*` بما فيها `PYTHONHOME` و`PYTHONPATH`: https://docs.python.org/3.14/using/cmdline.html.
- توجد عجلات Windows x86-64 لـ `pydantic-core` على CPython 3.14، وهو اعتماد ثنائي مهم لـ Pydantic: https://pypi.org/project/pydantic_core/2.41.5/.
